# Architecture

Two layers:

- **`FlowerPasswordCore/`** — a Swift Package (Swift 6 tools) with the pure logic: `FlowerPassword.swift` (the derivation algorithm), `PublicSuffix.swift` (registrable-domain extraction backed by the bundled `public_suffix_list.dat`), `ReleaseDecision.swift` (maps a decoded GitHub release manifest to an up-to-date/installable/manual-only outcome), and `TextUtilities.swift`. Unit tests live here, so pure, testable logic belongs in Core.
- **`FlowerPassword/`** — the app target (Xcode project) depending on the Core package. `main.swift` + `AppDelegate.swift` wire up the pieces; `AppState.swift` is the `@Observable` settings/state hub; `UI/` holds the AppKit panel form (observes `AppState` via `withObservationTracking`); `Shell/` holds the AppKit/system integrations (status item, floating panel, global hotkey via Carbon, clipboard auto-clear, self-updater, launch-at-login, dialogs).

## Key flows spanning multiple files

- **Localization**: `FlowerPassword/Localizable.xcstrings` is the single source of UI strings for `en` (source), `zh-Hans`, and `zh-Hant`. Every entry is manually managed (`extractionState: manual`), and `STRING_CATALOG_GENERATE_SYMBOLS` turns each key into a `LocalizedStringResource` symbol, so call sites read `String(localized: .memoryPassword)` and a missing key fails to compile; format specifiers become arguments (`.currentVersion(version)`). The language is resolved once by `Bundle.main` at launch: `Shell/LanguagePreference.swift` stores the menu choice as `AppleLanguages` in the app's own defaults domain (the same value System Settings › Language & Region › Applications writes) and the app relaunches to apply it. The brand name and the language names (English, 简体中文, 繁體中文) stay out of the catalog.
- **Self-update chain**: `Shell/SelfUpdater.swift` verifies release archives against the Ed25519 public key in `FlowerPassword/Resources/update-public-key.txt` (bundled as a resource). CI (`.github/workflows/release.yml`) signs archives with `scripts/sign-update.swift` using the `ED25519_PRIVATE_KEY` repo secret, and refuses to publish if the signature doesn't verify against that key. `scripts/release.sh` names the zip after the built app's `CFBundleShortVersionString` because `SelfUpdater.validate` compares archive version to runtime version.
- **Update handoff and rollback**: after validation, `SelfUpdater` copies `Resources/install-update.sh` into the staging directory and quits. The helper waits for the old process to exit, moves the installed bundle to `staging/previous.app`, swaps the new one in, and launches it through LaunchServices (`open -n … --args --update-ready <staging>/ready`). A direct exec would make the deleted `previous.app` the new process's TCC responsible process and break Accessibility until relaunch. If that file does not appear within 10 seconds, the helper restores `previous.app` and reopens it without telling the user. `AppDelegate` writes the file at the start of `applicationDidFinishLaunching`, before anything that can block. Every future release must keep doing this, or every in-app update will roll back.
- **Code signing**: CI re-signs the app with a fixed self-signed certificate (`SIGNING_CERTIFICATE_P12` / `SIGNING_CERTIFICATE_PASSWORD` secrets, used by `scripts/release.sh`), so the designated requirement is `identifier + certificate leaf` rather than a per-build cdhash, and TCC grants (Accessibility for auto-type) survive updates. Never rotate this certificate: every user would have to grant Accessibility again. Backup, restore, and recreation steps are in [release-signing.md](release-signing.md). Local builds without `SIGNING_IDENTITY` stay ad-hoc.
- **Releasing**: push a `v*` tag; CI fails unless the tag matches the app's `CFBundleShortVersionString`, so bump the version in the Xcode project first. On success CI creates the GitHub release (zip + `.zip.sig`) and auto-bumps the Homebrew cask in the separate `xlsdg/homebrew-tap` repo. A partial publish (release exists but an asset is missing) cannot be repaired by re-running — delete the release and re-run.
- **UI tests**: `FlowerPasswordUITests/` drives the real app with XCUITest, including an accessibility audit of the panel in both themes. The app launched with `--ui-testing` uses the private `org.xlsdg.flowerpassword.uitests` defaults suite (wiped at launch unless `--keep-defaults`), skips the global hotkey, and draws the panel tint opaque so the contrast audit measures the palette rather than the desktop behind it. Debug builds use the bundle id `org.xlsdg.flowerpassword.debug`, so a test run never terminates or reconfigures an installed release copy. Elements are found by accessibility identifier (`statusItem`, `password`, `key`, …); keep them when renaming views. Global shortcut, auto-type, launch at login, and updates stay manual: they need system permissions, change system state, or hit the network. CI runs them on every push to main and every PR (`test.yml`), and `scripts/release.sh` runs them before every release.
- **Clipboard → distinction code**: on panel show, a URL on the clipboard is reduced to its registrable domain (via `PublicSuffix`, lazily warmed off the main thread at launch) and prefilled as the distinction code.
