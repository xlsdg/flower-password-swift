# Architecture

Three layers, each depending only on the ones above it:

- **`FlowerPasswordCore/`** — a Swift Package (Swift 6 tools) with the pure logic: `FlowerPassword.swift` (the derivation algorithm), `PublicSuffix.swift` (registrable-domain extraction backed by the bundled `public_suffix_list.dat`), and `TextUtilities.swift`. `FlowerPassword.swift` is frozen (see AGENTS.md).
- **`FlowerPasswordDomain`** (second target of the same package, no AppKit) — `Settings` (persisted preferences, write-through to the injected `UserDefaults`), `Session` (the in-memory memory password and distinction code, never persisted, plus URL prefill), `PanelLayout` and `PanelPlacement` (pure geometry), and the orchestration that sits on system boundaries: `PasswordDelivery`, `ClipboardGuard`, `ShortcutChanger`. Those depend only on the protocols in `Ports.swift`, so they are unit-tested with fakes via `swift test`.
- **`FlowerPassword/`** — the app target (Xcode project), compiled with main-actor default isolation. `Composition.swift` builds the object graph once; `AppDelegate.swift` only holds it. `UI/` is the AppKit panel form, which applies frames from `PanelLayout` and observes `Settings`/`Session` via `withObservationTracking`. `Shell/` holds the AppKit/system adapters that implement the Domain ports (`SystemPasteboard`, `AutoTypeService`, `HotkeyManager`, `SystemDeliveryNotifier`) plus the status item, floating panel, browser URL reader, launch-at-login, dialogs, and `Updater` (Sparkle).

## Key flows spanning multiple files

- **Localization**: `FlowerPassword/Localizable.xcstrings` is the single source of UI strings for `en` (source), `zh-Hans`, and `zh-Hant`. Every entry is manually managed (`extractionState: manual`), and `STRING_CATALOG_GENERATE_SYMBOLS` turns each key into a `LocalizedStringResource` symbol, so call sites read `String(localized: .memoryPassword)` and a missing key fails to compile; format specifiers become arguments (`.currentVersion(version)`). The language is resolved once by `Bundle.main` at launch: `Shell/LanguagePreference.swift` stores the menu choice as `AppleLanguages` in the app's own defaults domain (the same value System Settings › Language & Region › Applications writes) and the app relaunches to apply it. The brand name and the language names (English, 简体中文, 繁體中文) stay out of the catalog.
- **Updates (Sparkle)**: `Shell/Updater.swift` wraps `SPUStandardUpdaterController`; `Info.plist` sets `SUFeedURL` (`releases/latest/download/appcast.xml`), `SUPublicEDKey`, and disables scheduled checks and profiling, so the feed is fetched only on "Check for Updates". Sparkle compares `CFBundleVersion`, which therefore tracks `MARKETING_VERSION`: a separate, never-bumped build number would make every release look older. CI (`release.yml`) runs Sparkle's `generate_appcast` with the `ED25519_PRIVATE_KEY` secret and fails if the appcast carries no `sparkle:edSignature` (the tool only warns when the key does not match `SUPublicEDKey`).
- **Code signing**: CI re-signs the app with a fixed self-signed certificate (`SIGNING_CERTIFICATE_P12` / `SIGNING_CERTIFICATE_PASSWORD` secrets, used by `scripts/release.sh`), so the designated requirement is `identifier + certificate leaf` rather than a per-build cdhash, and TCC grants (Accessibility for auto-type) survive updates. `scripts/release.sh` re-signs Sparkle's nested code inside-out with the same identity, and the app carries `com.apple.security.cs.disable-library-validation`: a self-signed identity has no Team ID, so the hardened runtime otherwise refuses to load `Sparkle.framework` (the Release app aborts at launch; Debug builds do not use the hardened runtime and hide this). Never rotate this certificate: every user would have to grant Accessibility again. Backup, restore, and recreation steps are in [release-signing.md](release-signing.md). Local builds without `SIGNING_IDENTITY` stay ad-hoc.
- **Releasing**: push a `v*` tag; CI fails unless the tag matches the app's `CFBundleShortVersionString`, so bump the version in the Xcode project first. On success CI creates the GitHub release (zip + `appcast.xml`) and auto-bumps the Homebrew cask in the separate `xlsdg/homebrew-tap` repo. A partial publish (release exists but an asset is missing) cannot be repaired by re-running — delete the release and re-run.
- **UI tests**: `FlowerPasswordUITests/` drives the real app with XCUITest, including an accessibility audit of the panel in both themes. The app launched with `--ui-testing` uses the private `org.xlsdg.flowerpassword.uitests` defaults suite (wiped at launch unless `--keep-defaults`), skips the global hotkey, and draws the panel tint opaque so the contrast audit measures the palette rather than the desktop behind it. Debug builds use the bundle id `org.xlsdg.flowerpassword.debug`, so a test run never terminates or reconfigures an installed release copy. Elements are found by accessibility identifier (`statusItem`, `password`, `key`, …); keep them when renaming views. Global shortcut, auto-type, launch at login, and updates stay manual: they need system permissions, change system state, or hit the network. CI runs them on every push to main and every PR (`test.yml`), and `scripts/release.sh` runs them before every release.
- **Browser tab / clipboard → distinction code**: on panel show, the first URL from the frontmost browser's active tab, then the clipboard, is reduced to its registrable domain (via `PublicSuffix`, lazily warmed off the main thread at launch) and prefilled as the distinction code. `Shell/BrowserURLReader.swift` asks Safari and Chromium browsers over Apple Events (needs the `com.apple.security.automation.apple-events` entitlement, which `scripts/release.sh` must pass again when re-signing) and reads Gecko browsers' `AXWebArea` URL only when Accessibility is already granted. It runs before the panel activates, because a first-use Automation prompt would otherwise dismiss the panel.
